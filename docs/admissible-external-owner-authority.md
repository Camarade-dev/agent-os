# The external, privileged owner-authority boundary

## Why this exists

An independent audit returned `CANARY_OWNER_ROOTED_WITNESS_AUDIT_FAIL` against
the previous owner-rooted design. The complete fake-owner world succeeded
because a single ordinary caller could, without any privilege:

1. choose a phrase;
2. calculate its digest;
3. create `OwnerAuthorizationStateStore`;
4. retain the expected digest;
5. create the retained seal;
6. obtain an `OwnerBoundVerifiedSerializationReceipt`;
7. pass the pre-effect gate;
8. consume the authorization.

Every step lived on the attacker's own side of the boundary. Reopening
attacker-controlled state and re-deriving attacker-chosen fingerprints proves
nothing, and no additional caller-generated hash, nonce, path, manifest or
self-signed record can fix that. The root of trust had to move outside every
process the caller controls.

## The trust root

Two strictly separate privileged capabilities now exist. The ordinary
preparation process, the controller, the backend and the coding agent possess
neither.

| capability | who | surface |
|---|---|---|
| installation / provisioning | root only | `installer.py`, `provisioner.py` — no RPC at all |
| runtime verify-and-consume | privileged broker | four operations on a fixed Unix socket |

An ordinary caller may still fabricate candidate stores, evidence packs,
receipts, tails, preparations, seals, phrases and digests. None of it helps,
because the caller cannot write the fixed privileged state, cannot provision
through the broker, cannot read the signing key, and therefore cannot produce a
receipt whose Ed25519 signature verifies against the public key named by the
root-owned installation record.

## Fixed layout

Production paths are module constants. `production_layout()` and
`attest_production_installation()` take **no arguments**, and no production
acceptance point exposes a path, key, socket or state-root parameter.

| object | path | owner | mode |
|---|---|---|---|
| configuration root | `/etc/admissible-owner-authority-v1/` | `root:root` | `0755` |
| installation record | `…/installation-v1.json` | `root:root` | `0444` |
| public verification key | `…/owner-authority-signing-key.v1.pub.pem` | `root:root` | `0444` |
| state root | `/var/lib/admissible-owner-authority-v1/` | `root:root` | `0700` |
| private signing key | `…/private/owner-authority-signing-key.v1.pem` | `root:root` | `0600` |
| authorization records | `…/authorizations/<record-id>/` | `root:root` | `0700` |
| runtime root | `/run/admissible-owner-authority-v1/` | `root:root` | `0755` |
| broker socket | `…/broker.sock` | `root:<launcher-group>` | `0660` |

A second, explicitly named `SYNTHETIC_..._LAYOUT` classification exists for the
provider-free privilege witness. It is a different classification, not a naming
convention, and `validated_production()` refuses it.

## Cryptographic primitive

Ed25519 (RFC 8032, pure form) through a **content-attested system OpenSSL**.
No cryptography is implemented in this repository; `signing.py` only marshals
bytes in and out of the executable.

The executable's path, device, inode, owner, mode and SHA-256 are recorded by
the privileged installer and re-verified on every use. Substituting an
`openssl` on `PATH`, or pointing at a byte-identical copy elsewhere, does not
validate — the inode differs. `PATH` is never consulted.

This route was chosen over a pinned Python dependency so that the packaged
wheel gains no new dependency and the isolated test environment needs no index
access to exercise the same primitive the real installation uses.

The private key is generated by the installer directly at its final root-owned
path, is never returned, never packaged, and never passed through argv, an
environment variable or IPC. Only the broker names its path.

## Installation identity

`installation_identity` is a fingerprint over the record's own identity plus
the **observed** file identities of the record and public key — path, device,
inode, owner, mode, content. It is bound into the signed receipt, into
`BackendExecutionAuthority`, and into the launch fingerprint through the OS
boundary authority's dependent authorities.

Consequences: a copied public record on another device attests to a *different*
installation; a record replaced, re-owned or re-moded after attestation is
caught, because the pre-effect gate calls `reattested()` on every effect; and a
caller-generated key at another path never validates, because only the fixed
path is ever read.

## The owner digest

```
sha256(EXTERNAL_CONSTRUCTION ‖ 0x00 ‖ phrase ‖ 0x00 ‖ canonical(payload) ‖ 0x00 ‖ record_id)
```

`record_id` is 32 bytes of entropy chosen by the **privileged provisioner**.
The caller does not choose it, cannot predict it before provisioning, and
cannot make the broker verify against a different one. This is what makes a
caller-precomputed digest worthless, and it is deliberately a different
construction label from the legacy self-rooted one, so a legacy digest can
never satisfy the external world.

Only the digest is retained. The phrase is read on a dedicated bounded
descriptor, used for one comparison, and never written, logged, returned or
fingerprinted on its own.

## Broker protocol

Protocol `admissible_owner_authority_broker_protocol_v1`, length-prefixed
canonical JSON on a Unix socket, with `SO_PEERCRED` checked against the
authorized launcher uid on every connection.

**Allowed**: `ATTEST_INSTALLATION`, `AUTHORIZATION_STATUS`,
`VERIFY_AND_CONSUME`, `RECORD_LAUNCH_RESULT`.

**Absent by construction** (asserted by a schema test, not by review):
provisioning an authorization, setting an expected digest, changing a payload,
selecting a state root, selecting a signing key, signing caller-supplied
messages, resetting a consumed authorization, authorizing a retry or a repair.

There is no provisioning RPC. No public library function callable by an
ordinary process creates a production pending-authorization record: the entry
point refuses a non-root effective uid, and the production `authorizations`
directory is root-owned mode `0700`, so an unprivileged copy of the provisioner
fails on both counts.

## One-time ordering

Durable states, forward-only:

```
PROVISIONED_PENDING → PHRASE_VERIFIED → CONSUMED_LAUNCH_COMMITTED
                    → RECEIPT_ISSUED  → LAUNCH_RESULT_RECORDED
```

`VERIFY_AND_CONSUME` proceeds **only** from `PROVISIONED_PENDING`. Each
transition is an `O_CREAT|O_EXCL` marker creation followed by `fsync` of the
file and its directory.

### The chosen rule, and its proof

**Consumption strictly precedes receipt issuance, inside one broker-side
transaction.**

*Exactly one winner.* `consumed.json` is created with `O_EXCL`. Two concurrent
launchers race on a single atomic filesystem operation; the loser gets `EEXIST`
and refuses. Correctness does not depend on the lock, which only orders work.

*No crash restores launchability.* The consumption marker is durably fsynced
**before** the broker asks OpenSSL for a signature. Therefore at every crash
point:

- crash before the commit → state is at or before `PHRASE_VERIFIED`, no receipt
  ever existed, and the record is not launchable because `VERIFY_AND_CONSUME`
  requires `PROVISIONED_PENDING` exactly;
- crash after the commit, before signing → the record is
  `CONSUMED_LAUNCH_COMMITTED`, which refuses; no receipt exists, so no launch
  can occur. Fail-closed;
- crash after signing → the receipt exists and the consumption is already
  durable.

There is no interleaving in which a receipt exists without a durable
consumption, and none in which a crash returns a record to a launchable state.
The alternative rule — sign first, consume afterwards — has exactly the window
this repair exists to remove: a valid receipt over a still-launchable
authorization.

`RECORD_LAUNCH_RESULT` is a terminal audit append that never restores
launchability; it is what makes a *copied* receipt refuse when a second backend
tries to drive a launch from it.

## Signed receipt

The Ed25519 signature covers the canonical bytes of the receipt payload, which
binds: receipt schema and broker protocol; installation identity and id; broker
signing-key fingerprint; authorization-record id and identity; the complete
canonical owner payload and its fingerprint (repository and implementation
HEAD, run and preparation identities, preparation root identity and retained
seal, candidate witness pack/receipt/nonce/tail, model policy and configuration,
executable and protocol identities, destination, mission, effects, budgets);
the one-time consumption identity and state; zero retries and zero repairs; and
the broker's terminal evidence, including the commit rule, the observed state
sequence, the consumption marker's file identity and the peer uid.

Backend and reconstruction verify the signature using **only** the exact
root-owned public installation identity. A copied receipt stays
cryptographically valid for its exact run and payload, and still refuses once
the launch is recorded or under another installation.

## Production closure

Production `HostCodexAppServerCapsuleBackend` accepts only a
`ProductionOwnerAuthorityWitness`: the exact signed broker receipt, the fixed
installation attestation, and the sealed `BackendExecutionAuthority`. Removed
from every production path: caller-created authorization state stores,
caller-retained expected digests, caller-selected state roots, caller-selected
public keys, self-generated owner-bound receipts, unsigned receipts and
non-production authorization modes.

The pre-effect gate revalidates, from scratch, on every effect: the broker
signature; the re-attested fixed installation identity; the exact authorization
record and its durable state; the complete payload; the reopened and
independently revalidated candidate witness; the fixed canary model policy; the
preparation seal against the externally retained identity; and the run identity.

The legacy self-rooted objects survive only in
`admissible.capsule.owner_authorization_non_production`, under names that say
what they are. They are impossible under a production execution authority:
`BackendExecutionAuthority` accepts only `SignedOwnerAuthorizationReceipt`, and
the legacy type is not that type and cannot be converted into it. A payload
built for one world is refused by the other, in both directions.

## Synthetic privilege witness

`tests/_owner_authority_privilege_witness.py` runs inside a disposable user and
mount namespace where it genuinely runs as uid 0, and demonstrates the
privileged installer identity, root-owned state with a `0600` key, a launcher
view in which the key has no path at all, a root-owned `0660` socket with peer
credential validation, a signed one-time receipt, concurrent-consumption
exclusivity, the crash window, and refusal of the complete fake-owner world.

Two limits are reported rather than hidden:

1. it is a temporary directory, not `/etc`, `/var/lib` and `/run` — the
   production attestation takes no arguments and can never be pointed at it;
2. this host has no `newuidmap`, so a user namespace can map exactly one uid.
   Installer and launcher therefore share a *kernel* uid, and the key's
   inaccessibility is demonstrated by mount-namespace isolation rather than by
   DAC ownership. A real installation gets both.

The synthetic witness is not, and does not claim to be, a real privileged
installation.
